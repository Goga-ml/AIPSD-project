# Pattern Journal · Ghmertoto (Otar Khunashvili) · Weeks 1 to 4

*One entry per teaching week: where I applied the pattern, what I delegated, how it was verified, what I noticed, and what I would do differently. Written 20 October 2026, drafted by Claude Code from the actual build of the Interview Technique Coach (see `delegation.md`, Entry 5).*

---

**W1 · Context as Budget** · *Written 2026-10-20.*
**Where I applied it:** the classifier sends the model only the interviewer questions as `L<line>: <text>` plus a fixed rubric, and never customer answers, header metadata or word counts. **Delegated:** writing the prompt and the validator to Claude Code. **Verified:** `test_prompt_contains_only_interviewer_questions` fails if any customer turn or header text reaches the prompt. **What I noticed:** the live Gemini runs showed about 450 input tokens but about 2,500 output tokens per interview, because thinking tokens count as output; my spec guessed 900. **Do differently:** run one real call before writing the cost estimate, and budget output tokens as carefully as input.

**W2 · Spec Before Code** · *Written 2026-10-20.*
**Where I applied it:** `spec.md` was written and approved before any code existed, with three success criteria and three acceptance criteria that a script can decide, including an error case (malformed line, empty transcript). **Delegated:** drafting the spec; I chose the folder name and repo and approved it before the build started. **Verified:** the agent reread the spec against its own criteria and found it contradicted itself (null share "if either total is zero" vs share 1.0 with no customer turns), and fixed it before coding. **What I noticed:** the spec was also wrong in ways code review could not catch, such as the default model name (`gemini-2.5-flash` returns 404 for new keys) and the token estimate. **Do differently:** write the error criteria first, and mark every number in a spec as measured or assumed.

**W3 · Uncertainty-Aware UX** · *Written 2026-10-20.*
**Where I applied it:** the report says labels are "model judgments, not facts". If the model fails, a question shows as "not classified" with no label and no guess, and the talk ratio, which code computes, is still shown. **Delegated:** the retry, validation and failure paths to Claude Code. **Verified:** tests for invalid JSON three times, API errors and a missing key, plus real failures in the live runs (503 overload, 429 quota), where the tool reported "unclassified" rather than inventing labels. **What I noticed:** my golden check first printed PASS on unclassified output; "nothing was classified" looked the same as "all correct". **Do differently:** make "no result" a visible failure from the first draft of any check.

**W4 · Grounded Generation** · *Written 2026-10-20.*
**Where I applied it:** every label is tied to a real line. The model must answer exactly the line numbers it was sent, and code rejects unknown lines, missing lines, unknown labels, `good` mixed with another label, and a rewrite on a good question. The numbers come only from code, and the report's rewrites keep the same research goal. **Delegated:** the output schema and checks; I created the Gemini key and kept it in an environment variable. **Verified:** `golden.py` compared real Gemini 3.8 Flash output with an answer key; interview_01 passed in 3 of 4 runs and interview_02 in 1 of 4, and the other attempts failed on overload or quota, not on wrong labels. **What I noticed:** the model's extra labels varied between runs (for example L14), so one run proves little. **Do differently:** run each golden question several times and record the pass rate, not a single result.
